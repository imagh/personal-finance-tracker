### 2026-10-30 — R8 on for release, early, with a shrink guard in `check`
- **Learning:** (1) Owner decision: minify the release build instead of moving sample and preview code to `src/debug`. R8 (`isMinifyEnabled` + `isShrinkResources`) is on from now; it was planned for H3. Signing, the SQLCipher keep rule and `ReleaseSmokeTest` stay in H3, and there is still no release `signingConfig` (fail closed). (2) `:app:verifyReleaseShrink` (in `app/build.gradle.kts`, wired into `check`) builds `assembleRelease`, reads `build/outputs/mapping/release/mapping.txt` and fails if `MainActivity` is missing or any `dev.imagh.pft.app.ui.theme.TokenSheet*` class survives. It was seen failing with minify off ("no R8 mapping") and with a deliberate `-keep` on `TokenSheetKt` (lists the leaked classes). (3) `proguard-rules.pro` has no keep rules: the release runtime classpath is only Compose and activity-compose, and the manifest-referenced `MainActivity` is kept by AGP. (4) Size: release APK 18,271,448 bytes unminified, 1,385,868 bytes with R8 (about 13x smaller). (5) Timing: cold `check --no-build-cache` took 24 s without the guard and 26-31 s with it; `assembleRelease` itself is about 15 s cold. (6) Smoke recipe on `pft35`: boot headless (`emulator -avd pft35 -no-window -no-audio -no-snapshot-save`, poll `sys.boot_completed`), `assembleRelease`, sign a **copy** of the unsigned APK in the scratchpad with `~/.android/debug.keystore` and build-tools 34.0.0 `apksigner` (one-off, never wired into the build), `adb install`, `am start -n dev.imagh.pft/dev.imagh.pft.app.MainActivity` (the class is in `dev.imagh.pft.app`, not the namespace root), then `pidof` after 6 s and a logcat grep (that pid) for `FATAL EXCEPTION|ClassNotFoundException|NoSuchMethodError`. Result: alive, no matches. Finish with `adb uninstall` and `adb emu kill`.
- **Why:** unminified release APKs shipped the token sheet and its `@Preview`; R8 errors for missing classes are cheaper to meet now than at the end of M1a.
- **How to apply:** add a keep rule only for something R8 reports or the smoke test shows broken, with a comment saying why. When a slice adds preview/sample code, add its compiled class prefix to `mustBeRemoved` in the guard (look it up in `app/build/tmp/kotlin-classes/release`). DS4's `ui/common/HeaderSamples` should be added when #17 merges. The SQLCipher/Room rules belong to A4a/H3.

### 2026-10-29 — Ledger foundations (A3): the audited write path and its fakes
- **Learning:** (1) `AuditedWriter` stamps the entity meta itself (`withMeta`), so a builder or update lambda cannot forge attribution or lifecycle state; entities implement `LedgerEntity<Id, Self>` (F-bounded) so the writer can do that without reflection. (2) The audit diff reads `auditFields()`, so every persisted business field must be listed. This is enforced in tests by `AuditFieldsCheck` (plain Java reflection over `declaredFields`, camelCase to snake_case, both directions plus value equality for simple types), which `InMemoryEntityRepository` runs on every write, so every entity test inherits it; `update` also fails closed (`IllegalStateException`) at runtime when the entity changed but no listed field did. A non-persisted field is not allowed on an entity (use a getter). A Kotlin value-class property keeps its property name and is stored as its underlying type, so typed ids and `Paise` need no special case. ARCHIVE/UNARCHIVE audit `archived_at`. (3) Identity and settings have no `EntityMeta`, so `AuditRecorder` is the one place an audit entry's id, time and attribution are filled in; it also breaks the cycle between `AuditedWriter` (needs `IdentityService`) and `IdentityService` (needs to audit its own setup). (4) `LedgerError` is sealed and its messages carry no user content. (5) The fake `TransactionRunner` snapshots every registered store at the outermost block and restores on throw; a failure at any depth marks the whole outermost block failed, even if an outer block swallows the exception (as with Room's nested `withTransaction`); it does not model savepoints. (6) `kotlin.uuid` cannot generate v7, so `Uuid7` is hand-written with a 12-bit counter (strictly increasing within a process, safe if the clock steps back); `NameBasedId` is UUIDv5 over a length-prefixed encoding and its output is pinned by tests because devices will store these ids. (7) A core module with only `suspend` contracts needs no coroutines library; it arrives with the first `Flow`. (8) Pre-commit does not run `check`, so a commit can pass the hook and still fail the coverage floor: run `./gradlew :core:ledger:check` before committing, and keep each commit's code and its tests together.
- **Why:** these are the invariants (INT-2, INT-3, INT-4, L-8) every later entity inherits; getting them wrong once would repeat in eight entities.
- **How to apply:** a new entity step implements `LedgerEntity`, lists all persisted fields in `auditFields()`, and writes only through `AuditedWriter`; its fake repository extends `InMemoryEntityRepository` and its test uses `LedgerTestKit` and `shouldHaveAudited`. Add the entity's errors to `LedgerError` and its id type next to the others.

### 2026-10-29 — Each session works in its own git worktree
- **Learning:** two Claude sessions shared the root checkout. One switched it to the A2 branch one second after the other created the DS2 branch, so DS2's six commits landed on top of A2 and had to be cherry-picked back out before PR #14. Owner rule: every session works in its own worktree.
- **Why:** a checkout has one HEAD; any session that switches branches there silently moves every other session's next commit onto the wrong branch.
- **How to apply:** before any branch work, `git worktree add <unique-parent>/personal-finance-tracker <branch>` and run every git, Gradle and file command there. Keep the folder name `personal-finance-tracker`: graphify titles `GRAPH_REPORT.md` after the checkout folder, and a DS2 refresh in a folder named `ds2-wt` committed that as the title. Give spawned agents the worktree path and forbid them from touching the root checkout. Never check out, reset or commit in the root checkout, run `git branch --show-current` before committing, and `git worktree remove` once the branch is pushed.

### 2026-10-29 — Roborazzi and native-graphics screenshots (DS2)
- **Learning:** Roborazzi 1.36.0 runs on our Robolectric 4.14.1 / Compose 1.7.5 / Kotlin 2.1.0 / AGP 8.7.3 with `@GraphicsMode(NATIVE)`; the native runtime resolves through Gradle (no extra download). `roborazzi.test.verify=true` in `gradle.properties` makes `check` verify, and `:app:recordRoborazziDebug` overrides it to record. A missing golden fails the test in verify mode (a useful red), and `check` runs the same goldens on the release unit-test variant too, so every golden must render identically on both. Gotchas: `captureRoboImage` only captures what is inside the window, so a tall sheet was clipped at 851dp until it was split into pages and captured by node bounds (`onNodeWithTag`); set the font scale with `LocalDensity` (`Density(density, fontScale)`) instead of a qualifier; one `setContent` per test, so drive pages with a state variable; `ui-tooling` adds an exported `PreviewActivity` that `ManifestHardeningTest` rejects (remove it in `src/debug/AndroidManifest.xml`); in Compose 1.7.5 the optical-size axis helper is `FontVariation.opticalSizing` and `Font(..., variationSettings)` needs `@OptIn(ExperimentalTextApi::class)`; M3's default `Typography()` is `FontFamily.SansSerif`, not `Default`, so set the family on every role; detekt `MatchingDeclarationName` forces a file with one class to be named after it, and `TooManyFunctions` caps a file at 11.
- **Why:** goldens catch accidental visual change in the token sheet and later components; native graphics renders real glyphs, so a font or spacing change shows up in the diff. Verified by changing the hero letter spacing: all four screenshot tests failed.
- **How to apply:** record on one machine and review every changed PNG in the PR; re-record after a Robolectric, Compose or OS upgrade; keep goldens fake-data only and under 500 KB (the large-file hook). Never let a screenshot stand in for a behaviour test.

### 2026-10-29 — Adding a Gradle plugin to a locked, checksummed build (DS2)
- **Learning:** a new Gradle plugin cannot be added by following "Refreshing pins" step by step: the first resolve fails dependency verification because the plugin's POM has no checksum yet. Order that worked: (1) `buildEnvironment resolveAndLockAll --write-locks --refresh-dependencies --dependency-verification=lenient`, (2) the build-logic lock, (3) `--write-verification-metadata sha256 --write-locks --refresh-dependencies ...` for the full task list (without `--write-locks` that run failed the buildscript lock check), then prove it with a strict `check assembleRelease assembleDebug` on an empty `GRADLE_USER_HOME`. That fresh run still demanded `junit:junit:4.13.2` and `hamcrest-core:1.3` in the buildscript lock (a runtime dependency of `roborazzi-core-jvm`), fixed with `--update-locks junit:junit,org.hamcrest:hamcrest-core`; the warm cache had hidden it.
- **Why:** a warm cache passes while a clean clone fails, and a lock written in one mode can be incomplete in another.
- **How to apply:** after any plugin or test-library addition, run the strict build on an empty `GRADLE_USER_HOME` before committing; review the new lock and verification entries (they are trust-on-first-use).

### 2026-10-29 — Money text: sign-free formatter, null-on-reject parser, one amount limit
- **Learning:** `PaiseFormat.format` never emits a sign (a negative `Paise` formats as its magnitude, computed from the decimal string so `Long.MIN_VALUE` is safe); the caller (DS5 `MoneyText`) prepends U+2212 or `+`. `PaiseParser.parse` returns `null` for any rejected text (never throws), accepts a leading `₹` so `parse(format(x)) == x` holds, and rejects over-limit values and input over 32 chars. `Paise.MAX_AMOUNT` (Rs 1e11 = 1e13 paise) lives in `:core:money` because the parser needs a bound and cannot depend on `:core:ledger`; `LedgerLimits` should reuse it. A value class's generated boxed getter is never called from Kotlin, so a module of only one value class sits under the 90% JaCoCo line floor.
- **Why:** one sign owner avoids double signs and lets a signed balance reach the formatter; a bounded hand-written scan keeps untrusted amount text safe from regex backtracking and `Long` overflow.
- **How to apply:** UI never reformats money; it calls `PaiseFormat.format` and adds the glyph. A3's `LedgerLimits.maxAmount` should be `Paise.MAX_AMOUNT`. Note the design plan's DS5 hero-overflow example `₹10,00,00,00,000.00` is Rs 1e10, not the Rs 1e11 limit (`₹1,00,00,00,00,000.00`): use the real maximum in that test.

### 2026-10-29 — Header rule: serif only for the number, titles sans and away from it
- **Learning:** in rendered mockups, a serif title over a serif number was too heavy, and a sans title directly above a serif number clashed. What worked: the serif sets only the dashboard hero number; every title is sans, read-only and centred high in the header with clear space above the hero; the hero, its caption and the ‹ › period stepper sit low, in the thumb zone. The owner also split Budgets into a list tab and a detail page.
- **Why:** type pairing problems only showed once rendered at phone size; the wireframes looked fine. A read-only title can sit out of thumb reach, which frees the lower band for what you tap.
- **How to apply:** follow the "Header layout rule" in `docs/plans/2026-10-29-m1a-design-system.md` §3.4 (`CollapsingHeaderScaffoldTest` checks it). Put add actions in the FAB, never in the header. For visual questions, render an HTML mockup with headless Chrome and show the owner screenshots before writing the plan text.

### 2026-10-29 — DS1 colour tokens and theme: what to know before DS2
- **Learning:** (1) The brand scheme was generated with `@material/material-color-utilities` 0.3.0 (the engine behind Material Theme Builder), run once in a scratch directory; nothing from it is a project dependency. Its `themeFromSourceColor` returns the older surface roles, so the M3 1.3 roles (`surfaceDim`, `surfaceContainer*`) were filled from the same neutral palette at the current tone ladder (light 87/98/100/96/94/92/90, dark 6/24/4/10/12/17/22). (2) `ColorScheme` has no `equals`, so the theme tests compare a name-to-colour map of all roles. (3) `ColorContrastTest` first failed on dark `negative` against `surfaceVariant` (4.23:1). That role is a tone-30 fill for input tracks, not a surface amounts are drawn on, so the sweep covers background, surface, dim/bright and the five container steps (light tones 87-100, dark 4-24), as the plan says. (4) `ui-test-manifest` (the plan's debug-only dependency that registers the Compose test host activity) adds an exported `ComponentActivity` to the merged **debug** manifest, so `ManifestHardeningTest` went red on debug; as `debugImplementation` it is also absent from the release unit-test task, where `createComposeRule()` then fails to resolve the activity. So the dependency is dropped and `HostedComposeRule` registers `ComponentActivity` with Robolectric's package manager instead (`createAndroidComposeRule<MainActivity>()` does not help: it refuses `setContent` once the activity has content). (5) Writing locks first needs `--dependency-verification=lenient` (new artifacts are not yet in the metadata); then append the checksums with `--write-verification-metadata sha256 --refresh-dependencies --rerun-tasks --no-build-cache` and review the diff, which must be additions only. (6) `enableEdgeToEdge()` is observable under Robolectric only through the bar icon appearance (`WindowCompat.getInsetsController`), not through bar colours, which the theme already makes transparent.
- **Why:** each of these cost a failed run or would have produced a test that cannot fail.
- **How to apply:** regenerate the whole scheme, never single roles, if the seed changes; keep `pft_window_background` equal to `BrandColors.*.surface` (`WindowThemeTest` checks it); use `HostedComposeRule`, never `createComposeRule()`, in this module so Compose tests run on both debug and release unit-test tasks.

### 2026-10-29 — Design direction: premium Cashew, calm money colours
- **Learning:** the owner wants Cashew's look made more premium: one-hand layout (content from mid-screen), iOS-like springs, system sans-serif for daily screens and Newsreader serif (set looser than its defaults) for dashboard numbers only (titles are sans; see the header-rule entry above). Green and red are kept for meaning, not decoration: expense rows and positive balances are neutral, while totals, over-budget and negative balances carry colour. The accent comes from the system, with indigo `#4A55B8` as the fallback.
- **Why:** colour everywhere reads as noise. The light green and red are nearly equal in lightness, so colour alone can't carry meaning for colour-blind users.
- **How to apply:** build every screen from the design-system plan's components (`docs/plans/2026-10-29-m1a-design-system.md`). Give every amount a sign or word, not only a colour. No font or emoji downloads: the app has no network.

### 2026-10-29 — Gate the scan on what ships; report the tooling
- **Learning:** the first full scan found 64 CVEs at CVSS ≥ 7, but none were in code that ships. About 58 were grpc/netty/protobuf inside AGP's `_internal-unified-test-platform-*` configurations (emulator test tooling). One Kotlin compiler CVE (CVE-2026-53914, build-cache deserialization) was CPE-matched onto every Kotlin jar, including the shipped `kotlin-stdlib`. One was an Apache Ant task under JaCoCo.
- **Why:** gating on every configuration keeps the scan permanently red on a pinned, two-year-old toolchain, and a gate that's always red gets ignored.
- **How to apply:** the default `dependencyCheckAggregate` gates `releaseRuntimeClasspath` and `runtimeClasspath` only; `-PscanAll` reports everything without failing. Read a finding's "Referenced In Project/Scope" before acting on it. Suppressions need a reason and an `until` date. Plan the Kotlin ≥ 2.4.20 toolchain bump before 2027-01-31.

### 2026-10-29 — The vulnerability scan needs an OSS Index account, not just an NVD key
- **Learning:** dependency-check's Sonatype OSS Index analyzer is on by default, and OSS Index no longer answers anonymous requests. With only `NVD_API_KEY` set, the first run spent about 58 minutes downloading the NVD database, then every artifact errored in OSS Index and the task failed with "Analysis failed".
- **Why:** the failure only shows at the very end of the slow first run, and the per-artifact errors don't say "unauthorized".
- **How to apply:** export `OSSINDEX_USERNAME` and `OSSINDEX_TOKEN` (token in the Keychain) alongside `NVD_API_KEY`; the task now refuses to start without all three. Never paste a token into an editor tab or chat. If that happens, rotate it.

### 2026-10-29 — A1 Gradle skeleton: five gotchas that cost time
- **Learning:** (1) JaCoCo **skips** `jacocoTestCoverageVerification` when there is no execution data, so a core module with production code and *no tests* passes the 90% floor silently (fail open). `pft.kotlin-core` adds `requireTestsForProductionCode` to `check` to close it; we proved partial coverage fails (0.14 < 0.90), zero tests fails, full coverage passes. (2) The OWASP dependency-check plugin pulls `bcprov` 1.78 while AGP 8.7.3 pulls `bcpkix`/`bcutil` 1.77; the mix breaks AGP's `validateSigningDebug` ("Could not initialize class org.bouncycastle...") but not `check`, so the root build aligns every `org.bouncycastle` artifact on 1.78. (3) Libraries add manifest entries: `androidx.core` adds a `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION` uses-permission and `androidx.profileinstaller` adds an **exported** `ProfileInstallReceiver`; both are removed with `tools:node="remove"` and `ManifestHardeningTest` guards the merged manifest (it was red on both before the fix). (4) Convention plugins in `build-logic` must be Kotlin classes with the Kotlin/ktlint/detekt plugins `compileOnly` and loaded by the root build (`apply false`); precompiled `.gradle.kts` plugins need them on the runtime classpath and double-load the Kotlin plugin. (5) Robolectric's `ApplicationInfo` does not expose `dataExtractionRules`; the test reads AGP's merged manifest through `com/android/tools/test_config.properties`.
- **Why:** each one produces a green build that is wrong (1, 3) or a red build far from the cause (2, 4).
- **How to apply:** keep the guard and the hardening test; after any dependency bump run `./gradlew check assembleDebug assembleRelease` (not just `check`) and re-read the merged manifest test. Robolectric downloads its `android-all` jar from Maven Central at test time, outside Gradle's checksum verification; if that becomes a concern, pre-resolve it as a verified Gradle dependency and run Robolectric offline.

### 2026-10-29 — A1 review fixes: verification metadata must be generated against a fresh cache
- **Learning:** `verification-metadata.xml` written on a warm Gradle cache was incomplete: a fresh `GRADLE_USER_HOME` (or `--refresh-dependencies`) also downloads the `.pom`/`.module` files of versions that lost conflict resolution (junit-bom 5.9.x–5.11.x, jackson poms, ktlint's sarif4k/kotlin-logging) and failed verification on 17 artifacts. Fixed by re-running `--write-verification-metadata` with `--refresh-dependencies` in append mode, then proving a clean clone passes with an empty `GRADLE_USER_HOME`. Pruning compared against a minimal set generated from scratch: 36 stale entries were removed, all 1,248 shared checksums were identical, and the BouncyCastle 1.77/1.78.1 entries turned out to be required (AGP tooling configurations still resolve them). Separately, `requireTestsForProductionCode` now keys off test sources, since a leftover `build/jacoco/test.exec` let a module with deleted tests pass without `clean` (reproduced by restoring a real exec file by hand). The build scripts and `build-logic` are now linted from the root, which immediately caught a 134-character line and an overlong description string.
- **Why:** an incomplete checksum file passes on the author's machine and breaks the first clone; a gate that trusts a build artifact can be fooled by a stale one.
- **How to apply:** never `rm` the metadata file to refresh it (it drops prior checksums); follow "Refreshing pins" in `build-logic/README.md`, and test dependency changes against an empty `GRADLE_USER_HOME`. Keep lint covering anything the pre-commit command does not reach by default.

### 2026-10-28 — Slice branches can't nest under the base branch name
- **Learning:** git refuses `feat/m1a-foundation/a1-…` while `feat/m1a-foundation` exists, because a ref can't be both a file and a directory.
- **Why:** the `feat/<feature>/<slice>` topology in CLAUDE.md §6 cannot be created as written.
- **How to apply:** name slice branches `feat/<feature>-<slice>` (for example `feat/m1a-foundation-a1-gradle-skeleton`) and open their PRs into `feat/<feature>`.

### 2026-10-28 — App ID is permanent; build full export/import before ever changing it
- **Learning:** the applicationId `dev.imagh.pft` and the release signing key define the installed app. A sideloaded build with a different ID or key installs as a new app with an empty database.
- **Why:** changing either one without a migration path loses every transaction, the audit trail and the identities.
- **How to apply:** before changing the ID or rotating the key, first build and verify a full, encrypted export/import of all data (every table, including audit, settings and tombstones), with a round-trip equality test. Export, import, verify, and only then retire the old app. Rule recorded in `docs/plans/2026-10-28-m1a-core-ledger.md` Q4.

### 2026-10-28 — Reuse by layer: shared once two named consumers exist
- **Learning:** the owner wants code abstract at its own layer and reused, but no unnecessary abstraction. The M1a plan's §3.4 lists the shared building blocks per layer (`EntityMeta`, `AuditedWriter`, `EntityRepository`/`RoomEntityRepository`, `EntityListScreen`, `AmountField`, `AuditHistoryList`, …).
- **Why:** 8+ entities share the same lifecycle, columns, audit flow and screens. Copying that code per entity breaks the shared-code rule, but a generic framework breaks the abstraction bar.
- **How to apply:** extract a piece when the plan names two concrete consumers; prefer composition, with at most one level of generic base class and no generic service. In review, both re-implementing a shared block and adding a single-consumer abstraction block the PR.

### 2026-10-28 — graphify: commit the graph, not the machine
- **Learning:** `graphify claude install` writes the hook with an absolute path to one user's home and leaves a `settings.json.graphify-bak`. `graphify-out/` also holds a manifest with absolute paths, a cache and backups. `graphify update .` refreshes only code nodes, never docs.
- **Why:** a committed absolute path breaks the hook on the second machine, and committing the rest of `graphify-out/` leaks local paths and churns diffs.
- **How to apply:** hooks call `$HOME/.local/bin/graphify`; `.gitignore` lets through only `graph.json` and `GRAPH_REPORT.md`. Re-read the hook on every graphify upgrade. Use `/graphify . --update` when docs change.

### 2026-10-28 — Develop on the emulator; the primary phone never gets USB debugging
- **Learning:** the owner's phone runs payment apps, which often refuse to work with Developer options or USB debugging on. The emulator is the development device, and it can receive fake SMS (`adb emu sms send`), which suits M1b. On Apple Silicon, API 35 images fall back to software rendering unless started with `-gpu host`.
- **Why:** a sideloaded app can only be updated with the same signing key, and uninstalling wipes the encrypted database.
- **How to apply:** only release-signed builds go to the phone, installed from a file; create the release keystore before the first phone install. Feed the emulator only redacted, reviewed fixture text.

### 2026-10-28 — Toolchain pinned about two years old; the build tool is not the IDE
- **Learning:** the build toolchain (AGP 8.7.3, Gradle 8.10.2, Kotlin 2.1.0, JDK 17) is pinned to late 2024, but Android Studio stays current: a newer Studio opens an older AGP project fine. In current Studio the per-project JDK is the Gradle *JVM criteria* (`gradle/gradle-daemon-jvm.properties`); a JDK path in the Gradle *Distribution* field fails with "Gradle location is incorrect".
- **Why:** an old IDE misses security fixes and may not run on the current macOS; JVM criteria make Studio and `./gradlew` use the same JDK on both developers' machines.
- **How to apply:** bump the toolchain only deliberately and re-check the AGP/Kotlin/Gradle tables (TECHNICAL.md §7.1). Bend the age rule for security (JDK patches, SQLCipher, anything the vulnerability scan flags). AGP 8.7 caps compileSdk at 35.

### 2026-10-04 — EMIs are expenses; transfers and card bill payments are not
- **Learning:** an EMI payment is an expense linked to its loan entity. Transfers between own accounts and credit-card bill payments are not income/expense.
- **Why:** counts spending once and keeps the loan's outstanding derivable from linked EMIs. A card purchase converted to EMI would double count, so the original purchase is neutralised by linking it to the loan (PRD LN-5).

### 2026-10-04 — Bank SMS are untrusted input; parsing is templates only
- **Learning:** sender headers can be spoofed and scam messages mimic bank alerts. Parsing is deterministic and on-device; auto-logged transactions are flagged unverified.
- **Why:** a forged alert must never be treated as fact, and no message text may leave the device.

### 2026-10-04 — Builds run locally; keep logic in pure-Kotlin `core`
- **Learning:** the owner builds locally on a Claude Pro plan. The cloud environment also blocked `dl.google.com` (Android SDK), which no longer matters.
- **Why:** `core` modules test on a plain JVM in seconds, keeping sessions short and cheap.
