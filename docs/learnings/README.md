### 2026-10-30 — DS6e icon-only header actions: what to remember
- **Learning:** (1) `IconButton` is 40dp and its 48dp target lives outside the node bounds: assert `SemanticsNode.touchBoundsInRoot`, not `boundsInRoot` (the latter read 40dp and failed the first run). (2) `captureToImage` times out under Robolectric (`forceRedraw`), so pixel claims (which symbol, which tint) belong to Roborazzi goldens; unit tests assert semantics. (3) To assert "a symbol, not a glyph", look for `Role.Image` nodes in the unmerged tree and for no `SemanticsProperties.Text`; a text glyph wrapped in `clearAndSetSemantics` may carry no Text property either, so the no-Text check alone can be vacuous; the Image count is what went red. (4) `Icon` tints with `LocalContentColor`, so pass `tint = onSurfaceVariant` explicitly. (5) Nothing in release reaches the scaffold yet, so the release APK is byte-identical to the base: a zero delta here does not mean the drawables are free once A5 wires screens. (6) A sample-contract test and its sample change must share a commit with the goldens, but a stepper-only change can carry just the two goldens it moves; split commits by which pixels move.
- **Why:** each costs a failed run, a vacuous test, or a wrong size claim.
- **How to apply:** new header actions go through `HeaderIconButton` only; test touch targets with `touchBoundsInRoot`; re-measure the release APK when A5 first references `PftSymbol`.

### 2026-10-30 — DS6f font spike: what the measurements showed
- **Learning:** (1) **DM Sans has no `tnum` or `pnum`** and its default digits are proportional (advances 342 to 656 of 1000), so it fails the hard tabular-figures rule and is dropped. Figtree and Plus Jakarta Sans have `tnum` but their default digits are **also proportional** (equal only under `tnum`: 620 and 600 of 1000), so only the amount styles are tabular; neither has `lnum`. Check GSUB `tnum` as well as the default `hmtx`, and verify that `tnum` really maps all ten digits to equal-width glyphs (the probe followed the single-substitution lookups). (2) **Google Sans Flex** is OFL 1.1 with no Reserved Font Name, but the variable file is **3,910,784 B** (five axes, not six: `opsz`, `wdth`, `wght`, `ROND`, `slnt`), more than the whole 3 MiB font budget alone; the owner said "drop for now". A wght-only instance would be about 243 KB but is a modified font. (3) **R8 resource shrinking strips an unreferenced `res/font` file**: the first all-fonts release build added nothing until a throwaway `tools:keep="@font/*"` was added. Reference each font as `R.font.<name>` from reachable code, and look for the `res/*.ttf` entries (R8 renames them) in `unzip -lv` of the release APK. (4) **The release APK is 21,241,278 B, not 1.39 MB**: SQLCipher's native libraries (A4b, four ABIs, about 19 MB) are now most of it; the fonts add 35,171 B (Figtree) and 79,125 B (Plus Jakarta Sans) compressed. (5) google/fonts has **no static files** for these families, so static sizes (Figtree 120,376 B, Plus Jakarta Sans 289,720 B for 400+500+600) came from fontTools 4.55.3 instancing in a scratch virtual environment and are **indicative only**; variable files are smaller for both kept families. (6) Figtree's `wght` axis is 300-900 with **default 300**: declare each weight explicitly with `FontVariation.Settings(FontWeight(w))`. (7) On the emulator, variable weight does render: the same 48sp hero amount measured 634, 638, 642 and 660 px at `wght` 300, 350, 400 and 500, and a label that shows the measured width made this checkable through `uiautomator` while `FLAG_SECURE` blanks screenshots.
- **Why:** each would have cost a wrong turn in DS6h to DS6i: shipping a font without tabular figures, a budget blown by one file, a release APK that quietly lacks the font, an APK baseline that is 15 times smaller than the truth, and a hero weight chosen without evidence.
- **How to apply:** DS6h and DS6i follow the pick-ups in plan §6.1 (explicit weights, `tnum` in `TabularFiguresTest`, direct `R.font` references, pinned size and hash from the §3.7 table). Pull fonts only from the pinned google/fonts commit `6c1dbe27dcf7d817d4b62cec033ba77fa8e2a5ec`, into an empty scratch directory, and read them with `python3 -I`. For a throwaway device check, create a throwaway AVD (`ds6f_throwaway` on port 5556 worked) instead of using the shared `pft35`, and delete the throwaway worktree and AVD afterwards.

### 2026-10-30 — DS3 icons, palette and the glyph badge: what bit us
- **Learning:** (1) The official Material Symbols web SVGs have `viewBox="0 -960 960 960"`, so a vector drawable needs a `<group android:translateY="960">` around the unchanged path data; the repo's own `symbols/android` XML is absolute-coordinate and about 2x larger. `local_grocery_store` does not exist in Material Symbols (use `grocery`), so check every name against the pinned commit before relying on it. (2) A Kotlin formatter (ktlint) rewrote `"\uFEFF"`-style escapes in a test into literal invisible characters, silently changing what the test checked; build invisible or hostile characters from code points (`String(intArrayOf(cp), 0, 1)`) in tests. (3) Compose already gives any clickable a 48dp touch target (`SemanticsNode.touchBoundsInRoot` reports it), so a "touch target at least 48dp" test passes without `minimumInteractiveComponentSize()`; a mutation removing it did not fail the test, so the modifier was dropped as untested layout-only code. (4) `clearAndSetSemantics` on a clickable node does not drop the clickable's own role or action (peer semantics on one node merge, the inner modifier wins on a clash), so set `Role.Image` only when not clickable. (5) `TextLayoutResult.layoutInput.style.color` is how a Compose test reads the resolved text colour (pixels cannot be read, `captureToImage` times out). (6) `androidx.startup.InitializationProvider` is not on lint's classpath as a direct dependency, so declaring it in our manifest needs `tools:ignore="MissingClass"` (as the profile installer receiver does), and `android:exported="false"` silences `ExportedContentProvider`. Before the removal the merged manifest listed `EmojiCompatInitializer`, `ProcessLifecycleInitializer` and `ProfileInstallerInitializer`; only the first is removed. (7) A `GlyphSource.Emoji` with a lone surrogate, a bidi override or a zero-width space is refused; the England subdivision flag is 14 UTF-16 units, so a 16-unit cap still allows it. (8) The 92 drawables are 73 KB in the source tree, but R8 plus resource shrinking drop them from the release APK while nothing referencing `PftSymbol` is reachable from `MainActivity`; the release APK grew only by the licence asset (+4,337 B) until A5 uses the registry; a throwaway reference to every `PftSymbol` from release code measured +86,894 B (1,397,696 to 1,484,590), inside the plan's 90 KB budget. (9) `check` with a chained `&&`-less command in a shell script does not stop at a failed gradle run: gate commits on the exit status, a lint error got committed once and was amended.
- **Why:** each is a silent wrong turn (a rewritten test, a vacuous touch-target test, a build break found only by lint).
- **How to apply:** import icons with `tools/material-symbols` (never by hand), keep keys permanent, build hostile strings from code points, and add a lint-visible `tools:ignore` only with a comment saying why. When a consumer first references `PftSymbol` from release code (A5), re-measure the release APK; the registry then keeps all 92 drawables (about 73 KB source, less after resource shrinking).

### 2026-10-30 — Premium-look plan (DS6): facts found while planning
- **Learning:**
  1. `SettingsService` accepts only keys matching `[a-z][a-z0-9_]*`, so the design-system plan's dotted AP1 keys (`ui.theme_mode`) would have thrown `InvalidSettingKey`. AP1 uses `ui_theme_mode` and similar.
  2. The bundled Newsreader, read directly (cmap/GSUB/fvar/hmtx with a Python standard-library probe, no fontTools), has ₹ U+20B9, − U+2212, `tnum` and `pnum`, but **no `lnum`**. Its default digits are already equal-width (1100 units). Its `opsz` default is 18, not 48.
  3. By CAM16 and CIELAB hue, money warning amber is about 72–86°, not about 40°. Brass and champagne accents sit 1–9° from it, so hue cannot separate them; labels and palette-independent pill colours must.
  4. Dark tonal canvases reach tone 2.7, below the old contrast sweep floor of tone 4. Some light glow tints blend to tone 86.5, below its floor of 87. Sweep those colours by contrast, not by tone band.
  5. A git ref cannot be both a branch and a directory, so DS6 slices use `feat/m1a-foundation-ds6<x>-<slug>`, one worktree per slice.
  6. Owner, second round: the font budget is 3 MiB for all of `res/font`. An all-serif pairing was liked in the mockup but deferred; it can be added later as a new enum value with no migration, because unknown setting values read as the default. Keep persisted enums additive for exactly this reason.
- **Why:** each would have surfaced late, in AP1, in a red contrast test, or as a reviewer's "is tnum really there?".
- **How to apply:**
  - Validate setting keys against `SettingsService.KEY_PATTERN` when you design them.
  - Read font facts from the file before you depend on them, and still confirm the rendering on the emulator.
  - When you add a surface colour, add it to `ColorContrastTest` by value.
  - Do not assume a hue; compute it.

### 2026-10-30 — DS5: `hasVisualOverflow` lies, the real maximum is longer than the plan's, and a Compose test rule allows one `setContent`
- **Learning:** (1) In Compose 1.7 `TextLayoutResult.hasVisualOverflow` is true for any wrap-content `Text` narrower than its maximum width (`size` is the wrapped width, `multiParagraph.width` the constraint) and false when a `maxLines = 1` text is really cut off. A probe showed both. With the real maximum `Paise.MAX_AMOUNT` on a 300dp box the line broke after the minus sign and showed only "−", and `hasVisualOverflow` stayed false. Tests use line metrics instead (`isShownInFull()`: one line, `getLineEnd(0) == text.length`, not wider than its box). (2) The plan's hero-overflow amount (Rs 1e10) is not the limit; Rs 1e11 needs 16sp at 200% font scale on 393dp and 12sp on 320dp, so the shrink steps run 48 to 12sp and the hero wraps as a last resort instead of clipping. (3) `Dp.Hairline` lays out at zero height, so a divider using it has no measurable bounds; use one physical pixel (`1f / density`). (4) `captureToImage()` times out under our `HostedComposeRule` (native graphics), so tests check colours through pure mapping functions (`chipColors`, `groupedSectionColor`) and leave pixels to Roborazzi goldens. (5) A `ComposeContentTestRule` allows one `setContent` per test; drive changes through a `mutableStateOf` written with `runOnUiThread` and call `waitForIdle()` (with `autoAdvance = false` the update is not seen until you do). (6) Robolectric qualifiers must be in Android's order (`notnight` goes before the density) and `+` is only for method-level overrides, so tests simply drop `notnight` (the default). (7) detekt `MatchingDeclarationName` fires when a file has exactly one top-level class, so a small data class beside a composable goes in its own file (`ChipColors.kt`), and fake sample amounts use a file-level `@Suppress("MagicNumber")`. (8) Review found that the rolling-digit hero, one `Text` per character, cannot wrap, so it clipped digits where the plain hero wrapped; the fix drops the roll when the figure does not fit. The first version of its test (`bounds.width <= box`) could not fail, so a "fits" test must measure the thing that can overflow (the digit nodes' right edges), and be seen to fail first. (9) `MoneyText` throws in composition for a negative amount with a non-`Balance` semantic, so the ViewModel or mapper must pass magnitudes and test that.
- **Why:** each one produces a passing test that proves nothing (1, 4), a layout that cannot be checked (3), or a build error far from the cause (5 to 7); (2) is a money figure silently truncated.
- **How to apply:** assert fit with `isShownInFull()`, not `hasVisualOverflow`; size hero tests with `Paise.MAX_AMOUNT`; never render a money figure with `maxLines` and a clip as the only fit strategy; keep one `setContent` per test.

### 2026-10-30 — SQLCipher (A4b): the zeroed-key trap, the pairing result, and what the scan cannot see
- **Learning:** (1) **Room 2.7.1 + sqlcipher-android 4.7.2 works**, proven on `pft35` by `EncryptedDatabaseTest` (16 instrumented tests in all with `DbKeyManagerTest`): the file has no SQLite header and no readable value, a wrong key and an all-zero key do not open it, a fresh `DbKeyManager` + fresh `PftDatabase` reopen it, the audit triggers are installed, enforced and repaired, WAL mode is on. (2) **The zeroed-key trap.** `SupportOpenHelperFactory(byte[])` stores the array reference and `SQLiteConnection.open()` calls `nativeKey(mConfiguration.password)` for **every** connection it opens, including pooled WAL readers and the very first creation of the file. `DbKeyManager.useKey` zero-fills its array, so passing that array on would key later connections (and a first-run file) with 32 zero bytes. Wiping a copy after a successful open was tried: `laterConnectionsAreKeyedToo` and even `PRAGMA journal_mode` then fail with `SQLiteNotADatabaseException: file is not a database`. `DatabaseFactory` therefore opens eagerly inside the key block and gives SQLCipher its own copy that lives as long as the database (wiped only if the open fails). (3) **SQLCipher does not delete a damaged file**: `DefaultDatabaseErrorHandler.onCorruption` returns early when `hasCodec()` is true; a damaged header made the open fail and the file stayed. (4) **sqlcipher-android 4.7.2 bundles SQLite 3.49.1** (strings in `libsqlcipher.so`; 4.8.0 and 4.9.0 carry 3.49.1/3.49.2, 4.10.0 carries 3.50.4). OWASP dependency-check reports **0 vulnerabilities** on the release gate and nothing for the AAR in the `-PscanAll` run, because it cannot see inside native libraries; CVE-2025-6965 (SQLite before 3.50.2) and later 3.49.x CVEs are real for the bundled engine but need crafted SQL, which the app never runs. Left at the owner's pin; 4.10.0 is the fix (owner decision, needs the pairing test re-run). The androidx.sqlite suppression note records this. (5) The SQLCipher AAR ships its own consumer R8 rules (`-keep class net.zetetic.** { native; <init>; mNativeHandle ... }`); the release smoke ran clean on them alone, and `proguard-rules.pro` adds the planned conservative blanket anyway. Release APK grows from 1.4 MB to about 21 MB (four ABIs of `libsqlcipher.so`); an ABI filter is an H3 option. (6) Opening costs about 75 ms per connection key derivation on the emulator, so open off the main thread when A5 builds the container. (7) A force-stopped app leaves committed data in `pft.db-wal` (57 KB with a 4 KB `.db` on the emulator), which is why `PreMigrationBackup` copies the `-wal` too. (8) **Emulator snapshot boot can hang with adb `offline`**: cold-boot with `emulator -avd pft35 -no-window -no-audio -no-snapshot-load -no-snapshot-save -gpu host` and wait for `sys.boot_completed` (about 15 s). (9) Lock delta: `resolveAndLockAll --update-locks net.zetetic:sqlcipher-android` moved only that module and recorded the previously missing `androidTestImplementationDependenciesMetadata` lines; the verification metadata gained the AAR and its `.module` (the AAR sha256 equals Maven Central's). `androidx.sqlite` 2.2.0 (SQLCipher's runtime dependency) loses conflict resolution to Room's 2.5.0, so nothing else changed.
- **Why:** (2) would have produced a database "encrypted" with a publicly known key that still opened and passed every JVM test; (4) is a gap the automated gate cannot close.
- **How to apply:** never hand SQLCipher the array `useKey` gives you; use `DatabaseFactory`. When bumping sqlcipher-android, re-run `EncryptedDatabaseTest` (it pins the lazy-key behaviour) and read the bundled SQLite version from the `.so` (`strings jni/arm64-v8a/libsqlcipher.so | grep -E '^3\.[0-9]+\.[0-9]+$'`). B1's first migration needs an instrumented `migrate1To2` against `SupportOpenHelperFactory` (`Migrations.ALL` is empty at v1, so there is nothing to migrate on the encrypted file yet). M1b must handle credential-encrypted storage (`noBackupFilesDir` is unreadable before the first unlock after a reboot).

### 2026-10-30 — Room v1 (A4a): what bit us and what to reuse
- **Learning:** (1) **Room does not count a `@PrimaryKey` inside an `@Embedded` class** ("An entity must have at least 1 property annotated with @PrimaryKey"): entities using `MetaColumns` declare `@Entity(primaryKeys = ["id"])`. (2) **Robolectric serves the tested variant's merged assets**, not the `test` source set's, so `MigrationTestHelper` found no schema JSON with `sourceSets.test.assets`; the schemas are a `debug` asset dir (kept out of the release APK) and `MigrationTest` lives in `src/testDebug`. (3) **The schema JSON has no triggers**, so a helper-built old database has none: `MigrationTestSupport.createV1` installs them and seeds an audit row, and `migrateTo` fails unless they survived. A migration test therefore cannot skip the audit check. (4) Room 2.7.1's `withTransaction` is in `room-runtime` (no `room-ktx`), and its nested `withTransaction` already has the fake's semantics: an inner failure rolls back the outermost block even if an outer one swallows it. (5) An unannotated abstract `byId` in a generic base DAO that each entity DAO overrides with `@Query` works under KSP. (6) `pragma_table_info(?)` takes a bound parameter, so the Room-side audit-columns check stays parameterised. (7) `RAISE(ABORT)` surfaces as `SQLiteConstraintException`, and an unfiltered `DELETE FROM audit_entry` is blocked too. (8) Writing locks on a warm cache **drops `junit:junit:4.13.2` and `org.hamcrest:hamcrest-core:1.3` from `buildscript-gradle.lockfile`** (the pre-commit lint then fails with "not part of the dependency lock state"): re-add the two lines after any `--write-locks`. (9) `end-of-file-fixer` adds a newline to Room's exported schema JSON; Room does not rewrite it afterwards, so the committed file is stable. (10) With no `AppContainer` yet, nothing in release references Room, so only room-runtime's consumer rule keeps `PftDatabase_Impl`; the shrink guard now checks that, and a temporary release build (not committed) that opened Room on `pft35` ran clean under R8 (users, audit JSON, transaction, trigger abort). (11) The vulnerability gate failed on Room's runtime classpath: `androidx.sqlite` 2.5.0 (a wrapper library) is CPE-matched to the SQLite *engine* `sqlite:sqlite:2.5.0` and inherits its whole CVE history, and `kotlin-stdlib-jdk7/8` 1.8.20 gets CVE-2020-29582 (fixed in 1.4.21). Both are scanner false positives and are suppressed narrowly, with reasons and a 2026-12-31 expiry, pending the owner's decision; the real SQLite-engine question (CVE-2025-6965 needs SQLite >= 3.50.2) moves to A4b, which must check the SQLite that SQLCipher 4.7.2 bundles. `-PscanAll` also lists `sqlite-jdbc` 3.41.2.2, guava and the KSP/Room compiler jars (CPE false matches such as `processing:processing`): all build-time only. Lock/checksum delta: Room, `androidx.sqlite` 2.5.0, the KSP plugin and its build-time-only tail (`room-compiler`, `kotlinpoet`, `sqlite-jdbc` 3.41.2.2, guava), additions only.
- **Why:** each one cost a failed run or would have let a migration silently lose the audit triggers.
- **How to apply:** a new entity (B1) copies `RoomEntityRepository` + `MetaColumns` usage, adds its line to `AuditedTables`, registers a `Migration` in `Migrations.ALL`, bumps `PftDatabase.VERSION` and writes its `migrateNToN+1` test with `MigrationTestSupport` in `src/testDebug`. Build every database with `PftDatabase.create(...)` (it attaches the trigger callback and the migrations; the callback re-installs the triggers on every open, so a lost or replaced trigger is repaired). Never call `Room.databaseBuilder` for `PftDatabase` directly. Times are stored as epoch ms exactly: `EpochMillis.of` refuses a finer instant (no silent rounding), so A5's container must build core's `Clock` with `EpochMillis.clock()` (plan A5 acceptance criterion).

### 2026-10-30 — R8 on for release, early, with a shrink guard in `check`
- **Learning:** (1) Owner decision: minify the release build instead of moving sample and preview code to `src/debug`. R8 (`isMinifyEnabled` + `isShrinkResources`) is on from now; it was planned for H3. Signing, the SQLCipher keep rule and `ReleaseSmokeTest` stay in H3, and there is still no release `signingConfig` (fail closed). (2) `:app:verifyReleaseShrink` (in `app/build.gradle.kts`, wired into `check`) builds `assembleRelease`, reads `build/outputs/mapping/release/mapping.txt` and fails if `MainActivity` is missing or any `dev.imagh.pft.app.ui.theme.TokenSheet*` class survives. It was seen failing with minify off ("no R8 mapping") and with a deliberate `-keep` on `TokenSheetKt` (lists the leaked classes). (3) `proguard-rules.pro` has no keep rules: the release runtime classpath is only Compose and activity-compose, and the manifest-referenced `MainActivity` is kept by AGP. (4) Size: release APK 18,271,448 bytes unminified, 1,385,868 bytes with R8 (about 13x smaller). (5) Timing: cold `check --no-build-cache` took 24 s without the guard and 26-31 s with it; `assembleRelease` itself is about 15 s cold. (6) Smoke recipe on `pft35`: boot headless (`emulator -avd pft35 -no-window -no-audio -no-snapshot-save`, poll `sys.boot_completed`), `assembleRelease`, sign a **copy** of the unsigned APK in the scratchpad with `~/.android/debug.keystore` and build-tools 34.0.0 `apksigner` (one-off, never wired into the build), `adb install`, `am start -n dev.imagh.pft/dev.imagh.pft.app.MainActivity` (the class is in `dev.imagh.pft.app`, not the namespace root), then `pidof` after 6 s and a logcat grep (that pid) for `FATAL EXCEPTION|ClassNotFoundException|NoSuchMethodError`. Result: alive, no matches. Finish with `adb uninstall` and `adb emu kill`.
- **Why:** unminified release APKs shipped the token sheet and its `@Preview`; R8 errors for missing classes are cheaper to meet now than at the end of M1a.
- **How to apply:** add a keep rule only for something R8 reports or the smoke test shows broken, with a comment saying why. When a slice adds preview/sample code, add its compiled class prefix to `mustBeRemoved` in the guard (look it up in `app/build/tmp/kotlin-classes/release`). **DS4 follow-up (done after #17 merged):** `HeaderSamplesKt` and `ComposableSingletons$HeaderSamplesKt` are in `mustBeRemoved`; a temporary `-keep` on `HeaderSamplesKt` turned the guard red, and it is green with the real rules. `BottomActionBar.kt` also declares a preview, but it shares `BottomActionBarKt` with the real component, so a class-level guard can't single it out; it goes when nothing in release calls it. The guard counts classes R8 merged or inlined (`R8$$REMOVED$$CLASS$$N` in mapping.txt) as removed, requires `MainActivity` to map to its own name, and fails with "stale guard entry" if a prefix matches no compiled class. The SQLCipher/Room rules belong to A4a/H3.

### 2026-10-29 — DS4 motion and one-hand layout: Compose test and detekt traps
- **Learning:** (1) A semantics node's `boundsInRoot` includes a `graphicsLayer` scale or an `offset` only when `testTag` comes **after** that modifier in the chain; before it, the tag sits outside and reports the unscaled bounds. That is how `PressScaleTest` reads the 0.97 scale and the catalogue test reads a moving dot. (2) A `Modifier.composed` block does not recompose when state it read changes, so `animateFloatAsState(if (pressed) …)` there never moved; drive an `Animatable` from the pointer coroutine instead. (3) With `mainClock.autoAdvance = false`, call `waitForIdle()` between `advanceTimeByFrame()` calls; without it recomposition and coroutine resumes lag and transitions appear stuck. (4) A touch drag releases with fling velocity unless you hold still (`advanceEventTime(300)`) before `up()`; the snap tests need that to land 30% back and 70% forward. (5) M3's exit-until-collapsed `onPreScroll` collapses the header even when the list cannot scroll, so "content that fits keeps the header expanded" needs `canScroll` from the list state, and `canScroll` must stay true while partly collapsed or the header cannot be pulled back open. (6) M3 `TopAppBarState` is experimental (a file-level `@OptIn` is simplest); Compose lint's `UnusedMaterial3ScaffoldPaddingParameter` also fires in test code; `LocalConfiguration.screenHeightDp` follows the `h851dp` Robolectric qualifier, and the default Robolectric screen is 470dp tall, under the 560dp collapsed-only threshold, so catalogue tests that need an expanded header set a qualifier. (7) detekt `LongParameterList` (6) is ignored for `@Composable`; `MatchingDeclarationName` pushed `BottomBarAction` into its own file.
- **Why:** each cost a failed run or a test that passed for the wrong reason (verified by mutation: no snap spec, or `canScroll = true`, turns three header tests red).
- **How to apply:** put `testTag` after layer/offset modifiers when a test reads geometry; step clocks frame by frame with `waitForIdle`; hold still before `up()` in drag tests.
- **Deferred (not faked):** the plan §11 motion check (minified build, `dumpsys gfxinfo framestats`, under 1% janky frames) was not run: no emulator was running, so there are no numbers. It moves to C4, when a real list exists to scroll. Status-bar and display-cutout insets on a real device remain an emulator check.
- **Review follow-ups (same day):** (8) M3's `Scaffold` pads the list and FAB by `contentWindowInsets.bottom` only when the bottom-bar slot emits **no placeables** (read in `Scaffold.kt` 1.3.1: `bottomBarPlaceables.isEmpty()`); an always-present wrapper `Box` made the padding 0dp, so a screen without a bar put its last row under the navigation bar. `bottomBar` is now nullable. (9) Robolectric can express insets: `ViewCompat.dispatchApplyWindowInsets(LocalView.current, WindowInsetsCompat…)` after `setContent` drives `WindowInsets.safeDrawing` (navigation bar and IME tested). ### 2026-10-29 — Ledger foundations (A3): the audited write path and its fakes
- **Learning:** (1) `AuditedWriter` stamps the entity meta itself (`withMeta`), so a builder or update lambda cannot forge attribution or lifecycle state; entities implement `LedgerEntity<Id, Self>` (F-bounded) so the writer can do that without reflection. (2) The audit diff reads `auditFields()`, so every persisted business field must be listed. This is enforced in tests by `AuditFieldsCheck` (plain Java reflection over `declaredFields`, camelCase to snake_case, both directions plus value equality for simple types), which `InMemoryEntityRepository` runs on every write, so every entity test inherits it; `update` also fails closed (`IllegalStateException`) at runtime when the entity changed but no listed field did. A non-persisted field is not allowed on an entity (use a getter). A Kotlin value-class property keeps its property name and is stored as its underlying type, so typed ids and `Paise` need no special case. ARCHIVE/UNARCHIVE audit `archived_at`. (3) Identity and settings have no `EntityMeta`, so `AuditRecorder` is the one place an audit entry's id, time and attribution are filled in; it also breaks the cycle between `AuditedWriter` (needs `IdentityService`) and `IdentityService` (needs to audit its own setup). (4) `LedgerError` is sealed and its messages carry no user content. (5) The fake `TransactionRunner` snapshots every registered store at the outermost block and restores on throw; a failure at any depth marks the whole outermost block failed, even if an outer block swallows the exception (as with Room's nested `withTransaction`); it does not model savepoints. (6) `kotlin.uuid` cannot generate v7, so `Uuid7` is hand-written with a 12-bit counter (strictly increasing within a process, safe if the clock steps back); `NameBasedId` is UUIDv5 over a length-prefixed encoding and its output is pinned by tests because devices will store these ids. (7) A core module with only `suspend` contracts needs no coroutines library; it arrives with the first `Flow`. (8) Pre-commit does not run `check`, so a commit can pass the hook and still fail the coverage floor: run `./gradlew :core:ledger:check` before committing, and keep each commit's code and its tests together.
- **Why:** these are the invariants (INT-2, INT-3, INT-4, L-8) every later entity inherits; getting them wrong once would repeat in eight entities.
- **How to apply:** a new entity step implements `LedgerEntity`, lists all persisted fields in `auditFields()`, and writes only through `AuditedWriter`; its fake repository extends `InMemoryEntityRepository` and its test uses `LedgerTestKit` and `shouldHaveAudited`. Add the entity's errors to `LedgerError` and its id type next to the others.

### 2026-10-29 — Adding a Gradle plugin to a locked, checksummed build (DS2)
- **Learning:** a new Gradle plugin cannot be added by following "Refreshing pins" step by step: the first resolve fails dependency verification because the plugin's POM has no checksum yet. ### 2026-10-29 — Money text: sign-free formatter, null-on-reject parser, one amount limit
- **Learning:** `PaiseFormat.format` never emits a sign (a negative `Paise` formats as its magnitude, computed from the decimal string so `Long.MIN_VALUE` is safe); the caller (DS5 `MoneyText`) prepends U+2212 or `+`. `PaiseParser.parse` returns `null` for any rejected text (never throws), accepts a leading `₹` so `parse(format(x)) == x` holds, and rejects over-limit values and input over 32 chars. `Paise.MAX_AMOUNT` (Rs 1e11 = 1e13 paise) lives in `:core:money` because the parser needs a bound and cannot depend on `:core:ledger`; `LedgerLimits` should reuse it. A value class's generated boxed getter is never called from Kotlin, so a module of only one value class sits under the 90% JaCoCo line floor.
- **Why:** one sign owner avoids double signs and lets a signed balance reach the formatter; a bounded hand-written scan keeps untrusted amount text safe from regex backtracking and `Long` overflow.
- **How to apply:** UI never reformats money; it calls `PaiseFormat.format` and adds the glyph. A3's `LedgerLimits.maxAmount` should be `Paise.MAX_AMOUNT`. Note the design plan's DS5 hero-overflow example `₹10,00,00,00,000.00` is Rs 1e10, not the Rs 1e11 limit (`₹1,00,00,00,00,000.00`): use the real maximum in that test.

### 2026-10-29 — A1 Gradle skeleton: five gotchas that cost time
- **Learning:** (1) JaCoCo **skips** `jacocoTestCoverageVerification` when there is no execution data, so a core module with production code and *no tests* passes the 90% floor silently (fail open). `pft.kotlin-core` adds `requireTestsForProductionCode` to `check` to close it; we proved partial coverage fails (0.14 < 0.90), zero tests fails, full coverage passes. (2) The OWASP dependency-check plugin pulls `bcprov` 1.78 while AGP 8.7.3 pulls `bcpkix`/`bcutil` 1.77; the mix breaks AGP's `validateSigningDebug` ("Could not initialize class org.bouncycastle...") but not `check`, so the root build aligns every `org.bouncycastle` artifact on 1.78. (4) Convention plugins in `build-logic` must be Kotlin classes with the Kotlin/ktlint/detekt plugins `compileOnly` and loaded by the root build (`apply false`); precompiled `.gradle.kts` plugins need them on the runtime classpath and double-load the Kotlin plugin.
