### 2026-11-01 — A5b app container: what to remember
- **Learning:** (1) `AppContainer` keeps the open in a `Deferred` started on a container-owned `CoroutineScope(SupervisorJob() + io)` behind a synchronised `lazy`. A `Mutex` plus `withContext(io)` in the caller would be wrong: a caller cancelled mid-open discards the result, and the next caller opens the same file again. With the `Deferred`, `await()` cancellation only cancels the waiter. A failed open is cached as the failure and rethrown to every caller (no retry), so a second attempt can never create a second database over the first. (2) Never let a test throw an uncaught exception on a coroutine thread: kotlinx-coroutines-test, used by the Compose test rule, collects JVM-wide uncaught exceptions and fails a later, unrelated test (`UncaughtExceptionsBeforeTest` in `BottomActionBarTest`). Test "a failure propagates" at `AppContainer.open()` (the exception reaches the caller), not through a ViewModel. (3) A ViewModel that launches on an injected IO dispatcher (`LaunchViewModel`) can be awaited with a plain blocking wait on Robolectric's main thread; Compose tests use `compose.waitUntil`. (4) A test that must prove "the first frame does not wait for the open" needs an Application whose container is held open: `PftApplication` and `container` are `open` for `MainActivityOpeningTest`'s `SlowOpeningApplication`. (5) `data object` inside a sealed `LogEvent` passes `LogEventShapeTest` (its only field is a static `INSTANCE`).
- **Why:** a double open, a main-thread open, or a flaky cross-test failure is exactly what this slice is meant to prevent.
- **Follow-ups (documented, no code change):** (a) `AppContainer` caches `KeyUnavailable` for the process lifetime. For M1b, where the SMS receiver may trigger the first open at boot before the Keystore is usable, consider re-attempting only on the `KeyUnavailable` value, keeping "never retry" for thrown failures. (b) An unexpected exception from `container.open()` or `currentIdentity()` in `LaunchViewModel` crashes every launch while the cause persists (it fails closed, as documented); the A5f or diagnostics (H2) follow-up should decide whether the user should see a screen instead.
- **How to apply:** M1b's receiver calls `container.open()`, never `DatabaseStartup.open` directly. Keep new ViewModels' blocking-or-IO work on an injected dispatcher. In `check`, `PftRootReadyTest` lives in `testDebug` because the release `DevContent` is empty; A5f replaces it with nav-host assertions.

### 2026-11-01 — A5a safe logging: what to remember
- **Learning:** (1) detekt 1.23.7 **honours** a file-level `@file:Suppress("ForbiddenImport")` (placed before `package`, after any `//` comment): with it `SafeLog.kt` is clean, without it detekt reports `SafeLog.kt:7`. So the plan's fallback (`excludes: ['**/log/SafeLog.kt']`) was not needed. (2) `ForbiddenImport` has no source-set scoping, so the ban also hit two existing files that used `android.util.Log`: the instrumented `EncryptedDatabaseTest` (prints its own timing; given its own file-level suppress and reason) and the new `SafeLogTest` (uses `android.util.Log.INFO` spelled out, no import). (3) `LoggingScanTest` scans only production source sets, so those test files are not its concern. (4) The `LogEvent` shape check uses Java reflection (`declaredFields`, `permittedSubclasses`); no kotlin-reflect, and `Class.permittedSubclasses` works for Kotlin sealed interfaces on JVM 17. (5) The logging scan's `print(` rule needs a `(?<![\w.])` lookbehind so `footprint(` and `x.print(` are not hits (`System.out` is caught by its own rule). (6) Negative controls done by hand: a planted `println` in `src/main` fails `LoggingScanTest` with its path and line; a scratch `import android.util.Log` fails `./gradlew detekt`.
- **Why:** SEC-5 must hold by construction before any feature code can log money or names.
- **How to apply:** to log, add a `LogEvent` subclass with number/enum/duration fields in the change that emits it, add its sample to `LogEventShapeTest`, and call `SafeLog.event`. Never add a `String` field or overload; the shape test and the review reject it.

### 2026-10-31 — DS6i Plus Jakarta Sans: what to remember
- **Learning:** (1) A second sans cost one font, one enum entry and a helper: `sansWeights(resId)` now builds both families, and the `R.font.<name>` references stay direct (R8 kept `res/jj.ttf`, 176,288 B, 79,125 B compressed, exactly the +79,125 B DS6f predicted). (2) A slice that only adds an option can leave every golden alone: `git diff --stat origin/feat/m1a-foundation...HEAD -- app/src/test/screenshots` was empty, and the catalogue is not golden-covered. (3) Tests over code that landed one commit earlier pass on first run; use a negative control (here, Plus Jakarta Sans without `tnum` measures different widths) to prove the check can fail. (4) `FontBudgetTest` now pins the three font names and count, so a fourth font needs a deliberate edit. (5) `SansFont` entries are permanent names (`FIGTREE`, `PLUS_JAKARTA_SANS`, `SYSTEM`); AP1 only has to parse-to-default for unknown values. ### 2026-10-31 — DS6h bundled Figtree: what to remember
- **Learning:** (1) `FontVariation.Settings` needs the style too, `Settings(FontWeight(w), FontStyle.Normal)`; the plan's one-argument form does not compile in Compose 1.7.5. (2) Figtree's `wght` default is 300, so declare one `Font` per weight a role uses; `PftTypographyTest` checks every role weight (400 body, 500 labels and titles, 600 `headlineLarge`) is declared, so a new weight fails there first. Six text-free symbol-grid goldens did not change. (6) Tests that assert "the sans" must name it (`sansFamily(SansFont.FIGTREE)`), not `FontFamily.Default`. ### 2026-10-31 — DS6g type pairing: what to remember
- **Learning:** (1) A pairing picks roles and the display font picks what they are set in, so the builders take the `DisplayFont` choice (not a built `FontFamily`) and make one `newsreader(weight, size)` per role; the variation settings must never reach `SYSTEM_SERIF` or "Same as text". (2) A test can call `compose.setContent` once ("Cannot call setContent twice per test!"): loops over several pairings must call the pure functions (`pftMaterialTypography`, `pftType`) and one-config tests go through `PftTheme`. (3) Read a role's real axes off `FontListFontFamily.fonts.single() as ResourceFont` and `variationSettings.settings.associate { it.axisName to it.toVariationValue(Density(1f)) }`; do not restate the implementation's weight and size. (4) compose-ui-unit 1.7.5 has no `TextUnit.coerceIn`; clamp `size.value` and convert back. (5) Each extra catalogue toggle row shrinks the page area: under 560dp the Dashboard header starts collapsed and the scaffold owns its list, so its test needs a taller window (`@Config(qualifiers = "+h1000dp")`), not a scroll. (6) New golden names must not match an existing one: the type pages' titles still read "(sans)" because changing them would re-record the existing goldens. (7) A throwaway golden recorded under another name reappeared as an untracked PNG after a later `check`: delete it and read `git status` before `git add -A`. (8) The 16 KB zip alignment turns a ~1 KB `classes.dex` growth into a 16,384 B APK step; read the per-entry sizes, not just the total.
- **Why:** each cost a failed run, a vacuous test or a wrong claim (a pairing that leaked variation settings into the system serif; a header test that could not scroll).
- **How to apply:** AP1 persists `TypePairing` by `name` (`HERO_ONLY` default; an unknown stored value reads as the default) and adds it to the names test; all serif can come back as a third value with no migration. DS6h adds the sans family: the text family argument becomes the bundled Figtree, nothing else in `pftType` or `pftMaterialTypography` should change.

### 2026-10-31 — DS6d header glow: what to remember
- **Learning:** (1) You cannot probe "the header did not recompose" with a `SideEffect` in a slot lambda (`actions`, `hero`): the header's parts are skippable, so the probe does not rerun when the header body does (it read 1 before and after). `Recomposer.runningRecomposers.value.sumOf { it.changeCount }` works: it counts once on leaving the expanded phase and stays flat across scroll frames; reading `collapsedFraction` in composition makes it rise. (2) A float `mutableFloatStateOf` compares with `!=`, so `NaN` as "unset" counts as changed on every write, and `-1f` collides with a real hero top (an integer position that is negative mid-collapse; a reviewer caught a frame at exactly -1 getting the Standard reach). Use `Float.NEGATIVE_INFINITY` (`NO_HERO_TOP`) and write once per layout. (3) Robolectric's `dynamicLightColorScheme` is synthetic: `primaryContainer` is tone 49 (light) and 60 (dark), not M3's 90 and 30, so a contrast sweep on it gives false failures (`onSurfaceVariant` 3.24:1 on the glow); sweep the dynamic wash by grey tone instead. (4) A Compose test class past detekt's `LargeClass` limit (`CollapsingHeaderScaffoldTest`) needs a new class, which then needs its own small `show`/pixel helpers. (5) `+notnight` is a Robolectric qualifier-merge syntax that only works in a method-level `@Config` layered on a class-level one; written into the class-level string it fails to parse (`failed to parse qualifiers`), so the class-level string is just `w393dp-h851dp-xxhdpi` (not-night is the default). (6) A new toggle row in the debug catalogue pushes later sections below the fold on a 393x851dp window; tests there scroll to their nodes with `performScrollToNode`.
- **Why:** each cost a failed or vacuous run.
- **How to apply:** to assert a scroll frame does no recomposition, compare the recomposer change count across steps and first assert it moved on a known recomposition. The glow is off by default, so a new golden that needs it sets `headerGlow = true` itself. The hero row stays untinted by construction (a circle on the top edge ending 24dp above the hero), and `HeaderGlowScaffoldTest` checks every pixel of that row: keep it when the header layout changes. Dynamic colour's wash is `primaryContainer`; re-check the contrast sweep if the derivation changes.

### 2026-10-31 — DS6c tonal surfaces: what to remember
- **Learning:** (1) `View.drawToBitmap()` on the compose host view works under `@GraphicsMode(NATIVE)` (read it inside `runOnUiThread`, after `waitForIdle`), where `captureToImage` times out: use it for "which colour did the real draw pass put here" tests (the scaffold's header and list, the bottom bar, the island fill and edge). It needs native graphics; the legacy mode draws nothing useful. (2) A one-pixel `BorderStroke` on a rounded island is rasterised at about 70% strength on the edge row (not the exact colour, one row each at top and bottom): assert "nearer the edge than the fill" and "the next row is the fill", not equality. (3) A default `ListItem` paints `surface` over whatever it sits on, so a list on the canvas needs `GroupedSectionDefaults.listItemColors()` in samples too; the header goldens showed a lighter list under a darker header until the sample did. (4) A temporary `FLAT` default let every consumer commit keep `check` green with the old goldens (FLAT reproduces the old look exactly); one commit then flips the default and re-records all 50 PNGs. A pixel-changing commit cannot be green without its goldens, so without that the consumers and goldens would have been one commit. (5) Screenshot wrappers and previews must sit on `PftTheme.surfaces.canvas`, not a bare `Surface`, or islands are drawn on the wrong background. (6) Adding a row to the debug catalogue's toggles pushed the Sections page content below the fold of a 851dp window; tests that `assertIsDisplayed` on page content should scroll to it first. (7) `MainActivity` is in the release APK, so `PftTheme`, the Graphite palette and `SyncWindowBackground` are reachable from release code (unlike DS6b/DS6e); the cost was +2,584 B of `classes.dex` and a release APK of the same size, 21,241,278 B, as the base.
- **Why:** each cost a failed run or would have given a vacuous pixel test.
- **How to apply:** DS6d adds the glow to `PftSurfaces` (a nullable field, off by default) and `wash` to `PaletteColors`, and its scaffold pixel tests can reuse the `drawToBitmap` helper. New screens take their background and cards from `PftTheme.surfaces` only; a new surface that carries money adds its colour to `ColorContrastTest`. A `NavigationBar` (A5/C4) uses `surfaces.island`. Never use light `surfaceContainerLowest` (white) as a card, sheet or dialog fill.

### 2026-10-30 — DS6f font spike: what the measurements showed
- **Learning:**
  1. **DM Sans has no `tnum` or `pnum`** and its default digits are proportional (advances 342 to 656 of 1000), so it fails the hard tabular-figures rule and is dropped. Figtree and Plus Jakarta Sans have `tnum` but their default digits are **also proportional** (equal only under `tnum`: 620 and 600 of 1000), so only the amount styles are tabular; neither has `lnum`. Check GSUB `tnum` as well as the default `hmtx`, and verify that `tnum` really maps all ten digits to equal-width glyphs (the probe followed the single-substitution lookups).
  2. **Google Sans Flex** is OFL 1.1 with no Reserved Font Name, but the variable file is **3,910,784 B** (five axes, not six: `opsz`, `wdth`, `wght`, `ROND`, `slnt`), more than the whole 3 MiB font budget alone; the owner said "drop for now". A wght-only instance would be about 243 KB but is a modified font.
  3. **R8 resource shrinking strips an unreferenced `res/font` file**: the first all-fonts release build added nothing until a throwaway `tools:keep="@font/*"` was added. Reference each font as `R.font.<name>` from reachable code, and look for the `res/*.ttf` entries (R8 renames them) in `unzip -lv` of the release APK.
  4. **The release APK is 21,241,278 B, not 1.39 MB**: SQLCipher's native libraries (A4b, four ABIs, about 19 MB) are now most of it; the fonts add 35,171 B (Figtree) and 79,125 B (Plus Jakarta Sans) compressed.
  5. google/fonts has **no static files** for these families, so static sizes (Figtree 120,376 B, Plus Jakarta Sans 289,720 B for 400+500+600) came from fontTools 4.55.3 instancing in a scratch virtual environment and are **indicative only**; variable files are smaller for both kept families.
  6. Figtree's `wght` axis is 300-900 with **default 300**: declare each weight explicitly with `FontVariation.Settings(FontWeight(w))`.
  7. On the emulator, variable weight does render: the same 48sp hero amount measured 634, 638, 642 and 660 px at `wght` 300, 350, 400 and 500, and a label that shows the measured width made this checkable through `uiautomator` while `FLAG_SECURE` blanks screenshots.
- **Why:** each would have cost a wrong turn in DS6h to DS6i: shipping a font without tabular figures, a budget blown by one file, a release APK that quietly lacks the font, an APK baseline that is 15 times smaller than the truth, and a hero weight chosen without evidence.
- **How to apply:** DS6h and DS6i follow the pick-ups in plan §6.1 (explicit weights, `tnum` in `TabularFiguresTest`, direct `R.font` references, pinned size and hash from the §3.7 table). Pull fonts only from the pinned google/fonts commit `6c1dbe27dcf7d817d4b62cec033ba77fa8e2a5ec`, into an empty scratch directory, and read them with `python3 -I`. For a throwaway device check, create a throwaway AVD (`ds6f_throwaway` on port 5556 worked) instead of using the shared `pft35`, and delete the throwaway worktree and AVD afterwards.

### 2026-10-30 — DS3 icons, palette and the glyph badge: what bit us
- **Learning:** (1) The official Material Symbols web SVGs have `viewBox="0 -960 960 960"`, so a vector drawable needs a `<group android:translateY="960">` around the unchanged path data; the repo's own `symbols/android` XML is absolute-coordinate and about 2x larger. `local_grocery_store` does not exist in Material Symbols (use `grocery`), so check every name against the pinned commit before relying on it. (2) A Kotlin formatter (ktlint) rewrote `"\uFEFF"`-style escapes in a test into literal invisible characters, silently changing what the test checked; build invisible or hostile characters from code points (`String(intArrayOf(cp), 0, 1)`) in tests. (3) Compose already gives any clickable a 48dp touch target (`SemanticsNode.touchBoundsInRoot` reports it), so a "touch target at least 48dp" test passes without `minimumInteractiveComponentSize()`; a mutation removing it did not fail the test, so the modifier was dropped as untested layout-only code. (4) `clearAndSetSemantics` on a clickable node does not drop the clickable's own role or action (peer semantics on one node merge, the inner modifier wins on a clash), so set `Role.Image` only when not clickable. (5) `TextLayoutResult.layoutInput.style.color` is how a Compose test reads the resolved text colour (pixels cannot be read, `captureToImage` times out). ### 2026-10-30 — SQLCipher (A4b): the zeroed-key trap, the pairing result, and what the scan cannot see

### 2026-10-29 — Ledger foundations (A3): the audited write path and its fakes
- **Learning:** (1) `AuditedWriter` stamps the entity meta itself (`withMeta`), so a builder or update lambda cannot forge attribution or lifecycle state; entities implement `LedgerEntity<Id, Self>` (F-bounded) so the writer can do that without reflection. - **Learning:** `PaiseFormat.format` never emits a sign (a negative `Paise` formats as its magnitude, computed from the decimal string so `Long.MIN_VALUE` is safe); the caller (DS5 `MoneyText`) prepends U+2212 or `+`. `PaiseParser.parse` returns `null` for any rejected text (never throws), accepts a leading `₹` so `parse(format(x)) == x` holds, and rejects over-limit values and input over 32 chars. `Paise.MAX_AMOUNT` (Rs 1e11 = 1e13 paise) lives in `:core:money` because the parser needs a bound and cannot depend on `:core:ledger`; `LedgerLimits` should reuse it. - **Why:** one sign owner avoids double signs and lets a signed balance reach the formatter; a bounded hand-written scan keeps untrusted amount text safe from regex backtracking and `Long` overflow.
- **How to apply:** UI never reformats money; it calls `PaiseFormat.format` and adds the glyph. A3's `LedgerLimits.maxAmount` should be `Paise.MAX_AMOUNT`. Note the design plan's DS5 hero-overflow example `₹10,00,00,00,000.00` is Rs 1e10, not the Rs 1e11 limit (`₹1,00,00,00,00,000.00`): use the real maximum in that test.

### 2026-10-29 — A1 Gradle skeleton: five gotchas that cost time
- **Learning:** (1) JaCoCo **skips** `jacocoTestCoverageVerification` when there is no execution data, so a core module with production code and *no tests* passes the 90% floor silently (fail open). `pft.kotlin-core` adds `requireTestsForProductionCode` to `check` to close it; we proved partial coverage fails (0.14 < 0.90), zero tests fails, full coverage passes. ### 2026-11-10 — Slice B plan: Room cannot declare CHECK constraints or partial indexes
- **Learning:** (1) Room builds a fresh install's tables from the `@Entity` classes, and an entity cannot declare a `CHECK` constraint or a partial (`WHERE`) index. A rule written only into a migration's SQL therefore holds on upgraded phones and silently not on fresh installs, and `runMigrationsAndValidate` does not catch it. The slice B plan keeps `currency = 'INR'` and tag-name uniqueness in core instead, and flags the same trap for C1 (`ledger_transaction.amount > 0`, `transaction_line.position > 0` and `amount > 0`). (2) Room validates a migrated schema against the entities, so a table cannot ship before its entity; tags got their own migration (v4) rather than sharing v3 with categories, which renumbers C1 to v5 and every later version by one at B-final.
- **Why:** a constraint that exists on only some databases is worse than none: tests on a fresh in-memory database pass while upgraded phones behave differently, or the reverse.
- **How to apply:** hold a data rule in core (or in a trigger installed by the database callback, like the audit triggers, which runs on both paths). Never put a `CHECK` or partial index only in a migration. When a plan names a schema version, check every merged plan and `data-model.md` for the same number.
